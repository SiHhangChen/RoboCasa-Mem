## 3. 已确认的整改点

### 3.1 专家模块与评测仍有耦合

9 个选定任务的 `runtime.py` 都直接导入 `expert.operations`，并把专家 handler
传给 `TaskRuntimeAdapter`。评测无需执行专家策略，但当前导入链仍要求这些模块存在。
应将专家组装改为录制路径加载，评测 runtime 不再直接导入专家代码。

初始化仍使用 `bench/execution/` 的位姿、导航或采样工具；评测观测和机器人状态
提取也使用其中的四元数工具。需要抽出公共功能后再裁剪专家执行目录。

### 3.2 资源依赖需要按用途拆分

9 个任务 YAML 都声明 `planner_script`。例如 WR08 配置加载时检查所有资源存在，
因此直接删除 MPlib 脚本会导致只做评测也无法加载配置。
应区分评测所需资源与专家资源，修改加载与校验逻辑。

导航路径和标定位姿不能按文件名一律删除：部分路径用于确定 episode 初始机器人
位姿。必须逐个核对初始化、场景和 evaluator 的实际引用。

### 3.3 任务白名单与公共模块

独立发布版需要同步裁剪 `bench/tasks/catalog.py` 与 `bench/tasks/__init__.py`
中的任务列表；环境注册应只加载发布任务。当前环境注册会遍历全部 builtin task。

静态审查选定任务的绝对导入发现：

- TM02 的柜子材质引用 WR01 的材质表；WR01 已在本次发布范围内；
- TM02 使用 `bench/tasks/wa02_button_asset.py`，这是共享模块，不能随 WA-02 任务移除；
- TS02 和 TM01 使用 `families/drawer_inspection/materials.py`；
- 多个选定任务使用公共 `button_asset.py`。

上述是直接静态导入结果，仍需用完整依赖审查与运行验证覆盖传递依赖、动态导入和
文件路径引用。

### 3.4 依据当前配置生成发布记录

历史 `configs/benchmark/release_locks/all_tasks_v1.json` 中 TS02 的身份记录与当前
源码不一致，例如旧任务版本为 1.0.0，当前为 1.1.0。
旧 lock 不作为选择发布评测预算或恢复旧配置的依据，不能直接筛选其 9 个条目作为
新发布 lock。

以实际运行记录及明确选定的 suite、它们引用的当前任务配置和运行行为为基线，
生成仅含这 9 个任务的专用 lock 与 suite manifest，不因旧 lock 差异修改评测规则。
旧全任务 lock 是历史文件，本次方案不直接覆盖它。
任务配置拆分会改变 config/resource hash，需要记录来源 commit 和版本对应关系，
并区分组织结构变更与评测语义变更。

现有全任务 lock 主要保存 seed 0 的条目；发布还应固定选定 suite 的内容 hash
及其全部 50 个 seed 的解析输入，而不是仅凭 seed 0 宣称完整评测已冻结。

### 3.5 安装、资源与资产

当前多个模块通过 `Path(__file__).parents[...]` 查找仓库根目录下的配置。
应明确包发现、资源打包和命令入口，使用可安装的资源定位方式，保证从任意工作
目录运行，不要求源代码 checkout 与输出目录相邻。

已复用 `membench` 当前的 3035 文件资产包，并记录完整路径、大小、SHA-256 和本机
逐文件校验证据，清单为 `configs/benchmark/simulator_assets.json`。该包已包含 WX-01
全部 8 种海绵及 WR-08 两种牛奶盒。旧收集脚本与旧文档不完整反映实际包内容，
不再根据它们要求从头收集。2026-10-20 已完成该包的 3035 文件恢复校验，以及当前
候选版在独立环境中全部 450 个正式任务输入的短步验收。资产包本身单独提供，许可说明与复原步骤见
候选版 `docs/THIRD_PARTY.md` 和 `docs/ASSETS.md`。

## 4. 实施顺序

1. 固定上述任务白名单与来源 commit，以已复制并核验的 suite 建立逐文件保留/排除清单。
2. 在开发仓库解除评测路径的专家导入和规划资源依赖，保持原录制入口可用。
3. 在隔离的发布目录中导出 9 个任务及依赖，裁剪任务注册和非发布入口。
4. 完成包资源、命令入口、固定环境、资产下载与模型接入文档。
5. 比较拆分前后的 episode 初始化、prompt、观测/动作合同和相同动作回放结果。
6. 按核验并明确选定的 suite 及其引用的当前输入生成专用 release lock 和 suite manifest。
7. 在干净环境验收后生成独立仓库和发布 tag。

## 5. 发布验收

- 任务发现准确返回这 9 个 canonical ID，不导入其他任务环境。

- fake policy 能通过协议握手和 preflight；短仿真验证初始化、步进与结果写入。

- 输出记录发布版本、suite hash、任务/资源身份、模拟器版本、模型合同与执行参数。
- 新发布 lock 和软件测试通过，仿真验证证据可追溯。
